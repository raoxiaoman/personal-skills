# 工作报告

从已归档日报和可验证的工作记录中整理报告。以事实为边界，合并重复事项，不把工具操作或未完成计划写成已完成工作。

**过滤低价值操作**：版本打包、构建产物生成、提交代码、同步文件、更新常规文档等过程性操作，除非它们同时代表已完成的提测、发版、验收或可交付结果，否则不要单独写入日报、月报或绩效材料。应记录它们背后的实际业务交付，例如“完成版本提测”或“修复某问题”，而不是“完成打包”。

## 成稿表达

直接写成可以使用的工作报告，不必再调用 prose-writing。自然感来自具体工作和真实判断，不来自口头禅、假细节或刻意随意。

- 围绕“做了什么、解决什么、做到哪一步”写清实际贡献，有可验证结果时再写结果。不把参与写成主导，不把提测写成上线，不把测试通过写成用户问题全部解决。
- 沿用用户材料中的说话位置和常用术语，绩效自评可用第一人称；不要模仿不存在的个人经历，也不建立作者画像。
- 用具体动作代替空泛评价，例如“统一三处状态判断”，少写“全面赋能、深度优化、显著提升”。没有测量就不写效率提升或收益百分比。
- 同类工作按需求、问题或交付结果合并。每段增加实际信息，不把同一成果换说法重复写，不为凑篇幅编造背景、困难和感受。
- 保持自然、朴实的书面语，不写宣传口号、论坛闲聊或强行升华。标点、列表与表格服从报告格式，不沿用通用创作的标点禁令。
- 材料不足时先写能确认的部分，关键缺口标为待补；仅在缺口影响报告含义时追问，不设置固定材料数量或字数门槛，也不联网寻找材料来冒充用户成果。
- 用户只要求改写现有绩效文字时，保留原有事实、范围和状态，不默认扫描 Git、生成表格、归档或覆盖文件。

例如，材料只有“拆分导出状态处理，编译通过，等待回归”，可写“拆分导出状态处理逻辑，已通过编译，等待回归验证”，不能写成“全面提升导出稳定性，明显降低故障率”。

## 报告类型与优先级

先判断用户真正需要的交付物。一个请求同时出现多个触发词时，只生成优先级最高的报告，除非用户明确要求全部输出：

1. **绩效**：绩效考核表、绩效自评、半年/年度考核。
2. **月报**：月度总结、月度工作汇报、指定月份回顾。
3. **日报**：今日工作、按提交写日报、某日工作记录。

日报是默认模式：用户只说“写工作报告”“整理今天工作”但未指定月度或绩效时，按日报处理。

## 日报

### 生成

**复制版优先**：用户最关心的是能直接粘贴的复制版。先只做采集和复制版，第一时间交付；
归档版属于第二批，可以慢。不要为了同时产出两份而让复制版等待。

第一批（要快）：

1. 用户未指定日期时使用当天；指定日期时按指定日期采集。
2. 运行：
   ```bash
   python3 /Users/raohui/.claude/skills/work-report/scripts/collect_daily_work.py \
     --date YYYY-MM-DD --author raohui --include-claude
   ```
3. 以 Git 提交为主，Claude 记录仅补充无提交的方案分析、验证或整理工作。
4. **立即输出复制版**，不要先写文件、先核对统计或先构思归档版。

复制版规则：

- 每一条事项及计划的正文不超过 20 个中文字符，编号不计入字数；超出时拆成多条，
  不用缩小字号、删减必要事实或把多项工作硬塞进同一条。
- **单个项目最多 6 条**。超出时先合并同类事项（同一需求、同一版本、同类 bug 优先合），
  仍超出则写为「其他 bug 修复（n 个）」或「其他工作（n 项）」。

归档版不受以上两条限制，保留全部细节。

合并示例：同一天两条无网提示修复（重试提示 No network、无网优先于超时长提示），
在复制版里合成「修复两处无网提示优先级」一条；归档版仍分开写清各自场景与提交。

格式：

```markdown
## 复制版
#开发
YYYY年M月D日
#项目名
1. 工作内容

下个工作日
1. 后续计划
```

第二批（复制版交付之后再补）：

6. 按同一事实展开归档版，不受 20 字限制，使用完整、可验证的中文表述；未给出后续计划时，只给 1–2 条保守计划。
7. 涉及具体提交时带上短哈希。
8. 不归档时到此为止，明确说明归档文件未被修改。

### 自动归档

生成日报后自动归档，不再等待用户确认。**归档在复制版和归档版都交付之后进行**，
不要为了赶归档而让复制版等待；归档结果与两份文案一起汇报即可。

用户明确说不归档时，跳过本节，并说明归档文件未被修改。

自动归档时：

1. 把归档版正文写入临时文件，交给归档脚本；不要手工编辑 `reports/{year}.md`。
2. 脚本负责插入条目并重算年度概览、各月汇总、关键里程碑与 `reports/README.md`。
3. 脚本会拒绝重复归档同一天，并会核对草稿日期与 `--date` 是否一致。
4. 归档或核对失败时如实报告，不把未写入的日报描述为已归档。

```bash
# 直接写入选定条目并同步统计（单次调用即可，脚本自带重复归档与日期校验）
python3 <skill>/scripts/archive_daily_report.py --date YYYY-MM-DD --file /tmp/draft.md

# 只想看会改成什么样时再加 --dry-run
python3 <skill>/scripts/archive_daily_report.py --date YYYY-MM-DD --file /tmp/draft.md --dry-run
```

脚本统计口径：「天」= 该项目当天出现；「项」= 该项目当天编号条目数；「下个工作日」不计入。
不要改成自然天数口径 —— 历史上有个别日期缺记录，自然天数会与既有统计对不上。

脚本会把「关键里程碑」重算为各月原始条目的前 8 条。若希望保留人工归纳的一句话版本，
先用 `--dry-run` 看改动，再单独微调该段；不要为此手工重算其余统计。

上述日报归档脚本仅适用于日报；月报在内容确认后询问是否保存，绩效遵循其生成与保存规则。

## 月报

### 生成规则

1. 先读取指定月份的归档日报；必要时用该月本人 Git 提交核验。共用解析器支持 1–6 级项目标题，带标题的「下个工作日计划」及其后项目内容也必须排除。
2. 按 `templates/monthly-report.md` 的网站表单结构输出：本月主要工作、本月亮点、本月困难／卡点。不要增加工作概览、交付与质量或下月计划等旧章节。
3. 每项分别写主要工作任务、任务成果情况、工作量（天）和状态。同一项目可按开发、适配、回归拆项；合并零散问题，不逐条罗列提交。
4. 每项「任务成果情况」用 `1.、2.、3.、4.…` 的数字序号分点，每点独占一行，每个任务从 1 重新编号；按实际成果数量列点，不为凑满四点拆句或添内容。用自然、具体的中文说明做了什么和做到哪一步，合并同类问题；提测不等于上线或验收。数字只写可验证的数量，不虚构通过率或效率提升。
5. 归档记录天数不等于实际出勤。工作量可以有小数，估算必须注明，合计与总天数一致；占比合计 100%，网站可自动计算。
6. 亮点选有事实支持的成果；困难写实际问题和仍需跟进事项，不能凭空编造阻塞。无法确认的状态留待确认。
7. 交付纯文本分段，便于逐字段复制，不用 Markdown 表格、代码块、图标或 HTML。

月报脚本只生成证据整理稿，不代替人工归纳。脚本输出的任务、工时和状态仍需核验后按模板改写，不能直接将关键词分类结果当成最终月报。

### 确认后询问保存

先交付可复制的月报草稿，改稿期间不自动保存。用户确认内容后，主动询问是否保存，并告知默认路径；只有用户同意保存后才写入。确认文案不等于授权保存，已明确要求保存时无需重复询问。

- 默认路径：`/Users/raohui/.claude/skills/work-report/reports/monthly/YYYY-MM.md`，月份补零，每月一个现役文件；用户指定其他路径时按指定路径保存。
- 保存用户确认的同一份正文，文件开头注明汇报月份和状态（已确认）；标记不混入网站字段正文。用户明确要求先保存草稿时，标为草稿。
- 写入前读取已有文件；已有同月版本时说明将替换它并取得覆盖授权，不覆盖其他月份或不相关内容。
- 保存后报告具体路径和状态；失败时如实报告，不宣称已保存。用户不保存或尚未答复时不写入。
- 月报保存不修改日报、年度统计或 `reports/README.md`，不调用日报归档脚本，也不自动向网站保存或提交。
- 月报是日报事实的派生稿，不作为新的日报事实来源，不自动回填缺失工作。历史月报仅在用户要求时补存，不从会话猜测确认或提交状态。

## 绩效

绩效请求优先于月报和日报。用户要绩效正文、自评或改稿时，直接交付文字，不强制生成 XLSX。只有要求考核表或 XLSX 时使用下方脚本，并遵循 xlsx 技能。现有脚本只支持 **2026 新模板 XLSX**，其他年份或模板先核对兼容性，不把脚本存在当作支持任意模板。

```bash
python3 /Users/raohui/.claude/skills/work-report/scripts/generate_review_2026.py \
  --year 2026 --half first --scores 92,91,90,88 \
  --output ~/Documents/绩效/2026上半年员工绩效考核表_饶辉.xlsx
```

- 文字起草优先使用用户提供的当期材料；需要从记录汇总时，再读取当期 `work-report/reports/{year}.md`，必要时以本人 Git 提交补充或核验。
- 根据实际工作整理重点，不强凑数量；表格任务项数量按模板和脚本能力处理，不把历史能力写成当期新增成果。
- `--scores` 传结果自评分数，逗号分隔；不传则全部默认 90。
- 生成表格前确认考核周期、年份、输出路径和自评要求；上下文已明确的信息不重复追问。生成后报告输出文件及待人工补充项。

**已知需人工处理的两项**（脚本默认值不代表个人判断，每次生成后手改）：

1. 任务权重默认 `0.25/0.35/0.20/0.20`，与常用取值 `0.35/0.25/0.25/0.15` 不同。
2. 工作达成效率（H 列）与工作态度（I 列）一律预填 90。

模板任务区不是固定行数，会按任务数量动态扩展，总分行与下方说明区随之顺延。
