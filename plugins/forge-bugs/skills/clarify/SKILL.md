# Bug 澄清

目标：低成本地把原始 Bug 整理为“背景、前置状态、复现步骤、预期结果、实际结果”。

可单独调用 `forge-bugs:clarify`；其他 Agent 可直接读取本文件。脚本位于本技能的 `scripts/bug_clarification.py`，下文命令使用本地源码安装路径；从其他目录加载时使用实际技能目录，不复制脚本。背景与预置词仍归用户的 `~/.claude/bug-context/`，不随插件安装缓存迁移或打包。整理不自动访问 Mantis；需要查询或更新工单时使用 `forge-bugs:mantis`，其他 Agent 可读取相邻 `../mantis/SKILL.md`。

## 触发判定

**新 Bug 默认先整理，再排查。** 这是 Bug 处理的常规入口，不是仅在看不懂描述时才调用的补救步骤。接到新的异常报告后，在搜索代码、提出根因或修改实现前先使用本技能。

以下输入均默认触发：

- 带有 Bug 编号、工单编号或测试编号，例如 `#1223M_2`、`1223M_2`；
- 没有编号的异常报告，包括测试、Mantis、聊天、截图说明或口述；
- 已包含前置状态、连续操作和异常结果，但仍未整理为标准结构的描述；
- “帮我修复”“查一下原因”“直接处理”等要求所附的新 Bug；明确要求修复不等于明确要求跳过整理；
- 对话或分支已经约定用于修 Bug，随后收到的每一个新 Bug。不能因为已有修复授权就省略整理。

仅以下情况跳过或不重复整理：

- 当前 Bug 已经具备背景、前置状态、复现步骤、预期结果和实际结果五部分结构；
- 同一 Bug 已在本轮对话整理过，用户只是继续排查、提供日志或回答问题；关键事实变化时只更新受影响字段，不从头重跑；
- 用户明确说“不用整理”“跳过澄清，直接查代码”等；
- 输入不是具体异常报告，例如讨论 Bug 概念、优化本技能或单纯提供分支用途。

**信息足够就直接整理，不反复追问。** 整理完成后默认提供“直接处理 / 补充内容”两个选项，并等待用户选择；此前的“帮我修复”“查一下原因”或分支修复用途不代替这次选择。只有用户已明确选择“直接处理”、明确要求跳过选择直接排查，或明确限定“只改写，不查代码”时，才按对应意图执行，不重复询问。关键事实缺失且会改变复现或结果含义时，先问一个最重要的问题。

有复现动作不代表已经完成整理。原文中的“可能是精度问题”等推测不能写成已确认根因；操作顺序不同导致结果不同等对照事实必须保留，不因压缩文案而丢失。

## 快速流程

1. 运行：
   ```bash
   ~/.agents/plugins/forge-bugs/skills/clarify/scripts/bug_clarification.py prepare --text '<原始 Bug>' --project '<项目名>'
   ```
   `--project` 可省略，也可按习惯写法传：脚本会先收敛到已登记的项目名（见下方「项目名识别」），再据此读取轻量背景缓存与项目预置词（只读文件，不搜索代码）。若返回的 `presets.exists` 为 `false`，先看输出里的 `presets.known_projects` 与 `project_warning` 确认名字是否用错；确认是尚无文档的新项目、且该功能确有稳定的对象词/模糊词/根因标记时，再按下方「项目预置词文档」生成文档并重新运行本步。
2. 结合原文、当前对话和脚本返回的少量背景整理文案：
   - 忠实保留 Bug 编号；
   - 只要原文涉及两个或以上同类对象（例如多个 clip、字幕、贴纸或页面），必须按首次出现顺序统一命名。命名形式为 `<对象词>A`、`<对象词>B`，更多对象依次用 C、D，`<对象词>` 取自对象类别本身（如 `clipA`、`clipB`，或字幕场景用 `字幕A`、`字幕B`），并在首次出现时明确它们的相对关系；后续所有字段都必须沿用相同名称，不得改回“前面的 X”“后面的 X”等不稳定指代；
   - 即使原文只描述“前面/后面”的两个对象，也必须转换为 `<对象词>A`、`<对象词>B`，例如“前面的 clip”写为 `clipA`，“后面的 clip”写为 `clipB`，并说明对应关系；脚本已按项目预置词中的对象词自动识别这类相对指代并给出建议；
   - 可以规范术语和补充稳定功能背景；
   - 不要把项目背景、代码实现或推测写成本次复现事实；
   - 不分析根因。
3. 若一个缺口会改变复现步骤、预期结果或实际结果：
   - 能从当前 context 立即确认就补充；
   - 只能通过一次明确、低成本读取确认时才读取；
   - 否则停止搜索，一次只问用户一个最影响描述方向的问题。
4. 信息足够后，先输出标准 Bug，再按「整理后的行动选择」衔接任务；用户补充时只更新受影响字段，不从头重跑。需要落盘时再运行校验：
   ```bash
   ~/.agents/plugins/forge-bugs/skills/clarify/scripts/bug_clarification.py validate --file '<文件>' --bug-id '#编号' --project '<项目名>'
   ```
   校验同样读取该项目预置词（模糊词、根因标记）；未传 `--project` 时回退到内置通用词表。

## 整理后的行动选择

整理完成或吸收用户补充后，默认调用实际可用的 `AskUserQuestion`，单选“接下来如何处理这个 Bug？”，提供以下两项，然后等待用户选择，不提前搜索代码或修改实现。

| 选项 | 描述 |
|---|---|
| 直接处理 | 按当前描述进入排查，并在授权范围内修复、验证；只授权分析时不修改代码 |
| 补充内容 | 继续补充步骤、环境、预期或实际现象，暂不开始排查 |

- 此前说“修复这个 Bug”“查一下原因”，不代表已选择整理后的“直接处理”；默认仍展示两个选项。
- 用户已明确选择“直接处理”（兼容“开始解 Bug”），或明确说“跳过选择，直接查代码”等时，不重复询问，在同一轮继续对应任务。用户在补充内容时同时明确说“直接开始修”，也按此处理。
- 用户明确限定“只改写描述，不查代码”时，只交付文案，不提供处理选项、不搜索代码。
- 关键事实仍缺失或新旧事实冲突时，先问一个会影响复现或处理方向的问题，不用选项跳过必要澄清；补齐后回到默认二选。

选择“直接处理”后，工具返回即在同一轮开始调查，不再问是否继续或只回复“准备好了”。遵循项目流程；若工作区未确定，先定位或确认工作区，不能凭空选项目。“直接处理”不包含提交、推送、安装、外部工单写入或删除用户数据的授权。

选择“补充内容”后，询问用户要补充的具体内容。收到后只更新受影响字段；没有关键缺口时重新提供“直接处理 / 补充内容”，不自动进入排查。

没有 `AskUserQuestion` 时，在摘要后明确给出文字选项“直接处理 / 补充内容”，并等待回复，不只停在“信息已补充”。

## 输出格式

```markdown
#<Bug编号> <简短标题>

## 背景
...

## 前置状态
- ...

## 复现步骤
1. ...

## 预期结果
...

## 实际结果
...
```

字段边界：背景写功能和对象关系；前置状态写操作前已成立的条件；复现步骤只写操作；预期和实际结果写可观察行为，不写原因。

## 成本限制

默认不做全项目探索、不调用子 Agent、不检索历史会话、不分析完整视频，也不为术语完美而搜索。非关键细节允许省略；关键动态事实缺失时直接提问。

## 项目名识别

项目名不再需要逐字对齐预置词文档的文件名：

- 显式传入的名字先按已登记项目收敛：忽略大小写与分隔符（`videoguru_android` = `VideoGuruAndroid`），并容忍平台后缀差异（`VideoGuru` → `VideoGuruAndroid`、`YouCut` → `YouCut_Android`）。
- 省略 `--project` 时，按当前 Git 仓库根目录名推断；worktree 归到主仓库的名字，不取 worktree 目录名。
- 收敛或推断发生过时，输出会带 `project_resolved_from` / `project_source: "auto"`；名字确实不存在时输出 `project_warning` 与 `presets.known_projects`，据此改名字，不要沿用兜底词表直接整理。

收敛只在「已登记项目里唯一匹配」时生效，多个候选或名字完全未知都保持原样，不会静默改到别的项目名下。

## 项目预置词文档

对象词、模糊词、根因标记按“项目”单独存放，而不是写死在脚本里；脚本只保留一份内置通用词表作为无文档项目的兜底。每个项目一份 JSON：

```text
~/.claude/bug-context/presets/<项目名>.json
```

| 类别 | 含义 | 示例 |
|---|---|---|
| `objects` | 本项目的对象词，用于把“前面的 X / 后一个 X”识别为 `<X>A/<X>B` | `clip`、`字幕` |
| `ambiguous_phrases` | 测试常用但含糊的表达，需要澄清 | `画面不对` |
| `cause_markers` | 常被误写成结论的根因词，写入“实际结果”要警告 | `状态丢失` |

首次遇到尚无文档的项目、或对象类别在项目中已稳定时生成；生成前先结合当前对话与代码确认对象词，避免凭空猜测。

`presets-set` 默认**按类合并**：只追加当前没有的词条，重复词（忽略大小写与分隔符）不会重复写入，未传的类别不受影响；返回的 `merged` 列出本次真正变化的类别。要删词或重建整个词表时加 `--replace`。脚本只读文件，需要新增/删除词条时用以下命令：

```bash
# 查看某项目当前生效的预置词（未生成时展示内置兜底，exists=false）
~/.agents/plugins/forge-bugs/skills/clarify/scripts/bug_clarification.py presets-get --project '<项目名>'

# 为项目追加预置词（默认按类合并，已有词条保留，只补没有的）
~/.agents/plugins/forge-bugs/skills/clarify/scripts/bug_clarification.py presets-set \
  --project '<项目名>' --objects clip --objects 字幕 \
  --ambiguous 画面不对 --cause 状态丢失

# 整类覆盖：只有确实要重建该类词表时才用
~/.agents/plugins/forge-bugs/skills/clarify/scripts/bug_clarification.py presets-set \
  --project '<项目名>' --objects clip --replace

# 列出已有文档的项目
~/.agents/plugins/forge-bugs/skills/clarify/scripts/bug_clarification.py presets-list

# 删除某项目的文档（删除后回退到内置兜底）
~/.agents/plugins/forge-bugs/skills/clarify/scripts/bug_clarification.py presets-remove --project '<项目名>'
```

对象词建议覆盖该功能可能成对出现的同类对象；不要塞入某次 Bug 的具体现象。文档缺失时对象识别自动关闭（`objects` 兜底为空），不报错。

## 学习与背景缓存

从使用过程逐步沉淀知识，不要每次重新搜索。用户明确确认、补充或纠正了可跨 Bug 复用的信息后，直接写入对应“项目 + 功能”的缓存，无需再次询问是否保存：

```bash
~/.agents/plugins/forge-bugs/skills/clarify/scripts/bug_clarification.py context-set \
  --project '<项目名>' --feature '<功能名>' \
  --background '<一条稳定背景>' \
  --term '测试用词=项目术语'
```

适合沉淀：正式术语、页面入口和返回关系、稳定对象关系、明确的产品规则。不要沉淀：某次 Bug 的现象、复现参数、猜测根因、临时实现和未经确认的预期。

后续同功能 Bug 优先复用缓存。用户纠正旧知识时先删除错误项，再保存新信息：

```bash
# 查看已有知识
~/.agents/plugins/forge-bugs/skills/clarify/scripts/bug_clarification.py context-list --project '<项目名>'

# 删除错误或过时的知识
~/.agents/plugins/forge-bugs/skills/clarify/scripts/bug_clarification.py context-remove \
  --project '<项目名>' --feature '<功能名>' \
  --background '<原背景>' --term '<测试用词>'
```
