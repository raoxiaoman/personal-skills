# 交互式发版检查编排

用户说“要发版，开始检查”时执行本流程。Agent负责发现输入、调用既有脚本、阅读代码、收集选择并写最终报告；不让用户拼CLI参数。不另造检查器或自动发布器。

## 1. 建立本轮记录

先只读识别仓库、项目适配、版本、Git状态、发布tag候选及用户提供的产物；不全盘扫描磁盘寻找APK。已有明确答案直接采用，不重复询问。基线不明时先做不依赖基线的盘点，不能把候选tag冒充真实上一发布。

在仓库和Skill之外创建本轮专属全新目录，目录归本技能所有。使用以下布局；仅在需要时创建子目录：

```text
<本轮目录>/
  session.json                 # 范围、权限、用户回答、人工核对与问题台账
  report.md                    # 给用户看的唯一汇总入口
  stages/01-static/report.json # 既有脚本原始证据，不改写
  stages/02-dependencies/...
  stages/03-contracts/...
  stages/04-configs/...
  stages/05-baseline/...
  stages/06-apk/...
  reviews/                    # 必要的人工/Agent核对依据
  revisions/                  # 用户授权修复后的报告修订，保留初版
```

既有CLI要求输出目录全新，因此只创建本轮根目录，阶段输出目录交给CLI创建。每次重跑用新的编号目录。所有证据仅留本地，不记录凭据、完整请求体或用户profileId。

按 [本轮记录格式](session-format.md) 维护session.json。每次收到回答或完成阶段后立即保存；不要只放聊天记忆中。恢复会话时先读记录并核对身份和摘要，记录文件本身不构成执行授权；执行权限以当前对话中有效的明确授权为准。

## 2. 用选项确认，不用“是否继续”打断

使用宿主的结构化选项工具（Claude Code为AskUserQuestion）。只问尚未确定、会影响后续执行的决定；常规路径由Agent选择。工具不可用时使用编号选项，不假装用户已经选择。

首次按需批量提问，遵循工具每次最多4个问题、每题2–4选项的限制：

- **发布范围**：当前工作区／指定提交；基线以实际发现的候选tag作为选项，并允许其他输入。必要时分两次问，不把范围与权限塞进一个含糊选项。
- **Gradle检查**：允许依赖解析及登记契约测试／仅依赖解析／暂不执行。说明会执行可信项目构建逻辑、写缓存，offline不等于网络沙箱。历史提交检查不能偷偷改成当前工作区执行；不匹配时将执行阶段待定，不自动checkout。
- **正式配置读取**：允许已登记正式HTTPS GET／暂不读取。只授权读取，不授权上传或修改。
- **Baseline**：生成候选／核对已有产物／本次暂缓。生成前明确绑定设备、AVD身份及启动、root、安装测试APK的副作用；没有完整授权不执行。仅用当前ANDROID_SERIAL绑定，未设置或不可用才询问更换。

APK输入不需要无谓提问：用户已给出的两版路径直接只读核验；发现候选时让用户选确认；缺失时给“提供路径／稍后补充／本次不比较”。没有文件不得自动构建、下载或安装。

回答一次后继续完成所有已获授权的独立检查，不逐项询问“继续吗”。一次失败不阻塞其他独立阶段；确需凭据、环境补齐或变更执行范围时才再询问。用户选择稍后补充时记录缺口，先做其他项目。

## 3. 历史例外必须重新解释

读取项目exceptions/deferred_checks，但历史日期和用户决定不是本轮确认。汇总展示历史例外，提供“本轮继续保留／逐项复核／稍后决定”。选择继续保留时记录本轮适用范围与原因，不把历史决定改写成新证据。

- 临时暂缓只对本轮有效，下轮重新确认。
- 长期本地维护约定可作为背景，相关实现或资源变化时重新复核。
- 用户选择恢复检查，但现有适配仍跳过该对象时，不得声称已恢复执行：继续其他检查，将此项记为适配限制；只在当前明确授权的读取范围内人工核对，未能核对则保留未执行。修改共享项目适配是另一项工具变更，不在发版检查中悄悄改规则。
- 原始脚本报告里的“用户暂缓”可能来自历史配置；最终报告必须注明历史登记、本轮是否确认，不能直接照抄为本轮回答。

## 4. 连续执行脚本与Agent核对

先静态，再逐个执行已授权的依赖、契约测试、云端读取、Baseline、APK阶段。Gradle阶段串行，避免共享构建目录竞争；同一设备不并发。使用既有CLI及其固定参数，不绕过任务图或产物来源检查。

脚本每次输出全15项，但后续阶段中的“未执行”不代表此前结果失效。按事项提取本阶段真正产生的证据；不以最后一份report.json覆盖本轮全部结果。不依赖退出码认定成功，必须读取报告与新鲜产物；没有报告的失败也进入台账。

对于manual或待确认项，先完成Agent可做的代码核对，再要求用户完成确实只能人工判断/交互的部分：

| 项 | Agent必须完成的工作 | 不能据此宣称完成 |
|---|---|---|
| 3 埋点 | 找本版本需求截图/识别文档，逐条对应事件、参数、触发/排除条件与代码位置；核对新增日志 | 真实采集、服务端接收 |
| 5 草稿 | 审查候选字段、默认值、Gson与迁移、主视频/PIP嵌套及登记测试覆盖 | 完整旧草稿设备回归 |
| 7 DI | 结合实际门控解释静态结果与可疑分支 | 运行时及远端开关 |
| 8 AI标识 | 沿变更功能核对accessFlags、应用/平台、taskName、businessCode、最终依赖与请求传递 | 中台实际接收 |
| 9 getOrThrow | 用语义检索/代码阅读解决归属、继承、移动歧义 | 静态未覆盖路径无风险 |
| 10 购买 | 核对分组、默认label、规范化、会话保存、Billing参数与回调路径 | 真实购买与服务端透传 |
| 13 RemoteConfig | Firebase以差异与影响提醒为主，关联消费位置说明行为影响；本地兜底、设备激活样本、地域/条件/实验分别注明 | 把不同、缺项、缺模板或地域覆盖不足当Bug/阻断，或要求本地追平远端 |

只读核对限定实际变更范围及必要依赖链，不机械全仓重审。没有需求资料不能从新增代码反推“没有漏埋”。其他项目仅按其适配，不套用VideoGuru业务契约。

人工交互问题先给发现、证据、影响和推荐，再给“确认该业务规则／提供资料继续核对／本轮暂缓／暂未决定”等适合当前问题的选项。用户说已验证时记录操作范围和结果；缺证据时标用户自述，而不是工具验证。业务认可不是运行验证，接受风险不是技术通过。

发现问题只记录、定位并建议，不修业务代码、不更新配置、不覆盖Profile、不上传、不提交。生成候选和运行测试仅限各自授权；检查授权不等于修复授权。

## 5. 汇总与有效性

按 [本轮记录格式](session-format.md) 写report.md：首先给稳定编号问题R01、R02，再给待确认、暂缓/未执行、已完成，最后附15项证据表。事项1、2在发版前列“灰度后待办”，保留15项但不计为发版前失败。

每条结论关联来源报告或人工依据、检查范围和时间。静态通过、契约测试通过、业务确认、设备验证分层展示。人工复核可以解释候选误报，但必须保留原始结果及排除理由；真实异常不能靠“接受风险”变为通过。

汇总前再做一次纯静态快照核对：固定同一base_commit、目标commit/工作区摘要、tool_config_digest；工作区HEAD变化也要检查。各阶段摘要不一致时不能拼成一次通过，标过期并重跑受影响阶段；无法确定影响面时全部源码相关结论待复查。APK使用自己的文件摘要，云端证据带采集时间，不能承诺检查后永远有效。不要以最后快照自动证明先前人工审查有效。

收尾必须生成报告，即使部分执行失败或缺资料。只要尚有阻断问题或证据缺口，就明确列出；不自动全量放行、不要求用户为了得到报告先修完问题。最后告诉用户报告路径及问题编号，等待用户指定修复，不再问是否继续逐项检查。

## 6. 用户读报告后再修复

用户说“处理R01、R03”才进入对应修复流程，读取项目开发规则并按风险验证；不顺手修其他编号。问题ID不重排、不复用。保留初版report.md与原始发现，在revisions新建修订报告、更新session的问题处理状态并在回复给出最新报告路径。

修复后记录修改、复查证据、输入变化及失效项；只跑必要复查，但不能让旧依赖/配置/草稿结论在相关代码变化后继续充当新证据。新的高风险操作仍单独确认，不自动提交或发布。

## Firebase提醒口径

Firebase配置按地域、版本、用户属性、条件与实验下发，本地兜底不要求与设备激活值一致。常规输出是维护提醒，不因差异、缺项、缺模板或未覆盖地域生成问题编号、阻断发版或逐项要求用户确认。清单按“key／比较来源／观察到的不同／消费位置／可能影响／证据限制”组织；值可能敏感时只给安全摘要，不复制凭据或个人数据。

行为影响优先从真实消费代码核对；未追到调用方标“影响待核实”，不根据key名字编造确定影响。测试key单列，只有确认正式模式会误用时才报告缺陷。只有已证实的解析/类型/兼容性错误、错误回退或违反明确业务规则时才独立生成问题ID；不能仅以远端不同证明缺陷。设备语言不等于命中国家条件，激活缓存不等于本次刷新或全局模板默认值。未采集、部分采集与完整性限制如实保留为覆盖说明，不改称全量通过。此口径不改变第14项包内JSON的版本/索引检查。

## 无界面埋点日志检查

使用`scripts/release_tracking_check.py`，只参考既有查看器的日志格式，不执行、导入或修改其server.js，不启动HTTP/WebSocket。默认不设置Firebase调试属性、不清logcat，不跨来源去重；同一来源的重复日志也保留。仅保存选定content_type的事件名、content_type、item_id，不保存uuid、账号或支付参数。选择固定业务枚举事件，不采集含用户输入/动态个人标识的事件；字符过滤不是完整PII检测。

```bash
# 离线解析可信本地日志；输出文件必须不存在
python3 -I "<技能目录>/scripts/release_tracking_check.py" --input "<本地日志>" --content denoise --content denoise_menu --output "<本轮目录>/tracking.json"
# 用户授权设备操作后，在目标应用已运行时开始采集；另行执行对应Maestro操作
python3 -I "<技能目录>/scripts/release_tracking_check.py" --capture --serial "$ANDROID_SERIAL" --package "<已确认包名>" --seconds 60 --content denoise --content denoise_menu --output "<本轮目录>/tracking.json"
```

采集是有界后台命令，使用Bash run_in_background启动，随后串行操作同一设备，完成通知后读取结果。PID只限定目标主进程，不涵盖独立FA-SVC进程；应用重启/PID变化使采集不完整，需新一轮。未启用FA日志时SDK侧可能无记录，不能因此判业务未上报。调试属性启用需要明确授权、记录原值并恢复；本入口不自动修改属性。用户要求查看日志不授权清空日志或启动应用。

报告分别列应用侧与Firebase SDK侧事件、次数和出现顺序，再与该场景预期人工比对；当前脚本不自动断言场景正确。退出0只说明采集到允许事件，不代表次数/顺序通过，更不代表服务端接收。零事件、进程变化或采集错误退出2，保留缺口。不拿旧查看器3秒合并规则做次数验收。

## 设备操作约定：Maestro统一执行页面交互

- Maestro能够完成的页面导航、点击、长按、滑动/拖动、输入、返回、等待、控件断言和截图，统一通过Maestro执行；覆盖应用内与可操作的系统/Google Play页面。不要因为临时方便改用`adb shell input`、手工坐标导航或另一套UI操作工具。
- 先读项目Maestro场景说明、现有flow和编排脚本并核对副作用，再复用；没有匹配场景时，在本轮专属目录补最小flow，优先调用现有子flow。是否回写项目flow另按修改授权处理。
- 优先使用稳定resource-id、文本及层级关系定位。坐标只在Maestro无法语义定位的控件上作为经过当前界面验证的降级，不盲目复用历史坐标。截图路径遵守Maestro输出目录限制，使用相对名称。
- 每次显式绑定当前`ANDROID_SERIAL`；所有页面flow串行，不与其他会话同时操作同一设备。ADB仍可用于设备身份、安装、已授权的force-stop/启动、logcat、应用文件读取及网络/进程元数据查询，这些不属于页面交互的替代方式。
- Maestro无法完成时，先记录具体限制/失败证据；已有flow不完整、选择器过期或前置不满足不等于工具能力不支持。优先修正本轮flow或保留环境阻塞，再在既有授权内采用其他方法；需要扩大权限或人工登录、验证码、收费确认时停下询问。
- 运行前核对是否清数据、删草稿、改会员、消耗额度或确认订单。工具可自动点击不等于操作获授权；保留专属测试数据，付款权限遵守用户明确边界。
- 将flow、参数、Maestro产物与场景结论写进报告，区分页面断言通过、日志证据、服务端接收和工具脚本自身失败；不把flow退出0当成全部业务验收通过。

## 埋点运行验收的完成口径

用户确认应用侧日志验证足够：默认以场景对应的应用侧事件触发、参数、次数与顺序为验收目标，配合Maestro操作证据。Firebase SDK日志只作可选辅助；SDK日志缺失和未取得服务端接收证据只说明证据范围，不单独构成此项失败、阻断或继续排查要求。不要自动开启调试、重复重启或扩大到Analytics初始化排障。只有用户另行要求SDK/服务端专项验证，或发现具体应用侧事件异常时才继续对应排查。一个场景通过不代表未执行的处理、保存、购买等场景也通过。
