# APK 包体分析

## 入口

确认旧 APK 和新 APK 的顺序。上下文明确时直接执行；路径或顺序缺失时才询问。先比较 APK 本身，不从当前项目配置猜测旧包内容。

使用本技能目录下的 `scripts/apk_size_analysis.py`，不要重写一次性 DEX 脚本。路径带空格时加引号：

```bash
python3 -I -B "<技能目录>/scripts/apk_size_analysis.py" \
  "/path/to/old.apk" "/path/to/new.apk" \
  --output-dir "<插件和项目之外的全新报告目录>" --top 20
```

- 不传 `--output-dir` 时只输出终端 Markdown。传入时同时保存 `report.md` 和完整 `report.json`，目录必须不存在且位于整个插件之外，避免误覆盖和把报告打包进插件。
- `--package-prefix 'com/example/app/=应用业务代码'` 可补充业务包归组，支持重复；脚本按最长前缀匹配。
- 退出码 0：分析完整；1：输入或运行错误；2：ZIP 比较完成，但至少一边 DEX 解析不完整。资源 split APK 无 DEX 也属于 2，此时 ZIP 数据仍可使用，不能宣称 SDK 归因完整。
- Python 使用 `-I`，不从 APK 或解压目录运行解释器。脚本不解压 APK；若另用工具提取文件，每个 APK 用独立新空目录，脚本放在其他目录，不执行包内内容。
- 不安装依赖；主脚本只用标准库。不自动构建、安装、上传或更改项目、混淆规则和依赖。

## 阅读报告

1. 先看 APK 文件净增量及对账。分类压缩增量加 ZIP 外开销增量必须等于文件大小增量。
2. 从 DEX、各 ABI 的 native 库、res、assets、resources.arsc 识别主因，同时说明抵消增长的减少项。
3. 看文件增减排行。资源文件名可能混淆，路径消失/新增不证明内容消失/新增。不同 DEX 的类会重排，不把 classes.dex 增长直接归给一个功能。
4. 看 DEX 包归组结构、类/方法数量与共享未分摊区域。**这不是 SDK 压缩后贡献**，也不能按数量或占比换算为 APK MB。代码混淆、内联、类合并后可能落入其他包。
5. APK 的 properties 是版本证据；R8 标记中 `backend=dex` 代表最终应用构建，`backend=cf` 可能是依赖预处理标记。没有找到标记不代表没用 R8。
6. DEX 不完整时保留 ZIP 结论，明确失败文件及原因，不利用部分数据做完整 SDK 排名。

## 按需追查依赖

当用户要具体原因，或 SDK 变化明显时，在用户指定的项目内只读核对：

- Gradle / version catalog 中实际依赖声明与版本变量。
- 对应配置的 Git 变更，找版本升级提交。默认只查目标配置的定向历史，不全仓库漫游。
- 本地 Gradle 缓存 POM / module，沿直接依赖确认传递来源。比如新增包可能由聚合 SDK 引入，不是应用自己单独接入。
- 区分“APK 直接证据”“历史配置证据”“当前缓存依赖证据”。当前 POM、当前版本变量不能自动当成旧 APK 的依赖清单。
- 如果有两次构建的 mapping，先把 `pg_map_id` 与各 APK 最终 `backend=dex` 标记中的 `pg-map-id` 精确匹配；不匹配就不使用。缺 mapping 时给包名前缀结果和限制，不强行认出所有混淆类。
- APK 架构、渠道、split/universal、debug/release 不一致时，先说明可比性限制。文件名只能作线索，不能作为确认。
- 跨包重命名后的内置依赖（shaded）不能通过普通 Gradle exclude 去重。删资源或排除传递依赖前需要 SDK 契约与验证，本技能仅提出建议，不擅自删依赖。

## 输出

默认中文，按以下结构给结论，不重复抄整个 JSON：

1. **结论**：旧/新大小、净增量、主增长类别。
2. **分类表**：实际压缩增量及抵消项，KiB/MiB 与十进制 MB 区分。
3. **主要来源**：SDK 包归组未压缩结构与可核验的版本、依赖链、提交证据。
4. **限制及建议**：剩余未归属区域、可比性、减包优先级及不可安全直接删除的项。
5. **报告位置**：Markdown / JSON 的本地路径及分析是否完整。

不把“看到了广告包增长”写成“每个 SDK 压缩贡献已精确分摊”，不把前缀统计的业务代码当作完整业务代码。
