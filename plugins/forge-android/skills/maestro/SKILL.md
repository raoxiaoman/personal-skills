# Maestro 设备回归

以项目真实入口、验收标准和设备证据为依据。包名、资源 id、fixture、账号和业务状态来自项目；模板中的 `<APP_ID>`、`<HOME_MARKER>` 不是可直接执行的配置。

## 先固定场景与权限

1. 阅读项目规则、已有场景和 flow，再按需查看实现与测试，确认前置、步骤、预期和可观察结果。
2. 先记录场景矩阵，再写脚本：列自动化范围、证据方式、副作用及清理动作。已有明确验收标准直接采用，只澄清影响执行的缺口，不重复要求确认。
3. 区分编写脚本与执行授权。清数据、删草稿、购买、消耗额度、改权益、安装或启动不能从普通脚本整理推导；确认开关也不替代用户授权。
4. 复用项目结构和公共 flow；新项目才按 [脚本架构](references/script-architecture.md) 建最小分层，不为单场景搭框架。

## 设计操作和断言

- 页面导航、点击、输入、返回、等待与断言优先用 Maestro。ADB 用于已授权的非页面操作；仅在有具体能力缺口或高频时间窗证据时降级，并记录限制。
- 优先稳定 resource-id、层级关系和受控文本；本地化文案限定支持语言。坐标仅作当前界面验证后的降级，不照抄历史像素；百分比也不保证跨布局成立。
- 先断言入口就绪，再执行操作并验证结果。页面未跳转不能单独证明拦截：还需点击命中、合理观察窗及业务状态等证据，排除按钮未响应或前置失败。
- 收口入口状态，或对互斥状态显式分支；不能把旧结果、缓存或前场景残留当成本轮成功。循环带上界，退出后断言目标。
- 按当前 Maestro 版本和设备检查 [能力边界](references/maestro-limits.md)。Toast、弹窗和时间精度的历史观察不是所有版本的普遍结论。

## 按需使用 shell 编排

常见理由包括跨调用保持页面状态、阶段间固定时间窗、切设备状态和多阶段组合，不限于这几类。普通加载先用状态等待；不能从 `Java.type` 失败推导 Maestro 没有任何等待能力。

确需编排时读取 [shell 编排](references/shell-orchestration.md)，使用 `templates/`，保持参数、阶段和失败位置可追踪。

## 绑定设备与恢复状态

- 仅使用当前 `ANDROID_SERIAL`；运行前 `get-state` 确认可用。显式 serial 与绑定冲突时拒绝，不枚举设备猜目标，不沿用历史序列号。
- Maestro 与 ADB 使用同一绑定，同一设备串行。换机必须先明确变更绑定，再记录 [设备契约](references/device-portability.md)。
- `device_wifi` 只切 Wi-Fi，不能证明完全断网；蜂窝、VPN、以太网和实际连通性另验。不为模拟断网擅自修改其他网络。
- 修改 Wi-Fi 前用 `restore_wifi_on_exit` 捕获原值；退出恢复原值并回读，恢复失败非零。已有 EXIT trap 时显式合并 cleanup，不覆盖旧清理逻辑。
- `device_ui_dump` 失败返回非零，不读历史 dump；`device_screen_size` 的屏幕尺寸不等于应用窗口。坐标换算仅限已确认的全屏、显示和折叠态。

## 执行与交付

先做 [隔离自检](references/verification.md)，再在授权设备上逐场景验证；失败后核对前置污染。按风险选择设备矩阵，单机结果有效但只代表该设备，不能扩大为跨设备通过。

分别报告自动断言通过、截图人工通过、失败和无法执行，附场景、设备、参数、产物及未覆盖范围。语法通过、退出 0 或截图存在均不等于完整业务验收；区分产品失败、脚本失败和环境阻塞。

收尾回读本轮改动的设备状态，按已授权范围处理专属测试产物；不自动删用户数据、提交或发布。
