# 脚本架构

## 三层

```
<项目>/
├── shared/       # 公共子 flow：跨功能的原语
├── tools/        # shell 编排 + 设备辅助库
└── <功能A>/      # 按功能分目录的场景脚本
    <功能B>/
```

- **shared/** —— 「怎么进到某个页面」这类原语。启动应用、打开列表项、选中元素、进入某功能入口。
- **tools/** —— 确需外部能力的编排，常见理由见 SKILL.md「按需使用 shell 编排」；不为简单 flow 机械增加包装。
- **功能目录** —— 一个场景一个文件，名字对应场景编号。

**入口差异和功能差异分别收敛。** 同一个功能可能有多个入口链路（列表入口、新建入口、从别处跳转）。入口链路各自抽成公共 flow，场景脚本只组合，不重复展开。

## 命名

用前缀表达「这个 flow 做什么」：

| 前缀 | 含义 |
|---|---|
| `goto-` | 完整链路，从启动一路到目标页面 |
| `open-` | 单步，从某个已知页面到下一个页面 |
| `enter-` | 进入并**收口**到某个确定状态 |
| `assert-` | 只做断言，不改状态 |
| `select-` / `pick-` | 选择类操作 |
| `prepare-` / `reset-` | 前置准备或清理 |

命名冲突要当心：`goto-xxx-from-draft`（链路）和 `open-xxx-from-draft`（场景）如果同名会让调用方读不懂自己在调哪个。**公共 flow 和场景脚本不要重名。**

## 幂等与收口

**不要假设进入时的状态。** 同一个页面在不同前置下可能是多种状态，硬写死一种就会在别的场景下失败。

两种处理方式：

1. **收口** —— 写一个 `enter-*` flow，内部把各条路径都收敛到同一个终态，调用方不必关心。

   ```
   # 已有结果 → 直接是结果态
   # 未处理过 → 先触发处理，再等到结果态
   # 两条路径都以「结果态」收口
   ```

2. **条件分支** —— 状态互斥且不需要统一时，用 `when` 分别处理。

   ```yaml
   - runFlow:
       when: { visible: { id: "<已展开的标记>" } }
       commands: [...]
   ```

   注意 `when` 的判断依据要选**当前状态特有**的元素。例如「菜单已展开就跳过、没展开才点」，不能无条件点 —— 菜单开着时再点一次会把它收起来，反而破坏前置。

**每个连接点都要有护栏。** 进入目标页面后先用一条断言确认「确实到了」，再往下走。否则失败信息会指向后面某一步，很难定位到「其实根本没进页面」。

## 断言策略

### 选择器优先级（跨设备视角）

同一份脚本要在语言、分辨率不同的设备上跑，选择器的选择顺序是：

1. **resource-id** —— 不随语言变，最稳
2. **`childOf` + index** —— 容器 id 稳定、列表项文案不固定时用（例如菜单第 N 项）
3. **产品固定的英文功能名** —— `REDUCE NOISE` 这类由产品定义、不参与本地化的文案可以写死
4. **多语言正则** —— 系统 / 应用本地化的文案，`text: "(画中画|Picture in Picture)"`，只列确实要支持的语言
5. **坐标** —— 有当前界面验证依据的最后手段，优先百分比；高频场景换算像素须核对当前显示与窗口

**不要写死的两类东西：** 本地化文案（换语言就失效）、从某次 dump 抄来的像素坐标（换分辨率就失效）。详见 `device-portability.md`。

### 断言落在用户可观察的行为上

优先顺序：

1. 与验收标准直接对应的结果状态，结合入口就绪与操作命中证据。
2. 目标页面或容器的可见性，排除遮挡、缓存和旧场景残留。
3. 需求关注的文本或数值，核对本地化与匹配边界。
4. 单独的元素存在性只能作辅助，不能证明可见、可操作或本轮产生。

### 用互斥状态做护栏

如果页面有 N 种互斥且必有一个可见的状态面板，就用这条组合断言「已经到达这个页面」：

```yaml
- extendedWaitUntil:
    visible:
      id: ".*id/(状态A|状态B|状态C|状态D)"
    timeout: 30000
```

比断言某一个具体面板更稳：既确认到了页面，又不假设进来时是哪种状态。

### 正反双向断言

关键结论配一条反向断言。

反例（弱）：`assertVisible: 结果面板` —— 可能是缓存残留或误判。
正例（强）：`assertVisible: 结果面板` + `assertNotVisible: 开始按钮` + `assertNotVisible: 解锁面板`。三者互斥，同时成立才算真的是结果态。

### 断言不到的地方

先检查当前实现和设备的实际层级；部分 Toast、短暂提示、播放位置或滑块数值未必可读。不能稳定观察时改验明确结果，或保留人工项。页面没跳转不能单独证明拦截，需结合入口就绪、点击命中、合理观察窗和业务状态，排除按钮未响应等原因。

## 副作用

每个 flow 头部写清楚：

- 会不会新建 / 删除草稿
- 会不会消耗云端处理额度
- 会不会改动账号权益
- 退出时是否计入一次撤销

有账号副作用的操作，用显式确认开关把住（见 `shell-orchestration.md` 的 `require_confirm`），并且**在脚本里也说明恢复方法**。

## fixture 设计

- 素材放设备上固定的目录，脚本按目录名切换，不依赖「最近」这类会变的默认目录。
- 单素材场景优先一个专属 fixture 目录只放一个文件，避免排序差异选错。多素材场景使用可核验的文件身份与顺序，不只按列表 index 猜素材。
- 素材要覆盖需求里的边界条件（时长超限、无音轨、静音、特殊尺寸）。边界素材单独放目录。
- 生成的素材把生成命令写进注释，别人能重建。
- **fixture 不随脚本走。** 换一台设备必须重新投放素材并触发媒体库收录，否则脚本会在「目录不存在」处失败。把投放方式（推送命令、目录名、收录方式）写进场景文档，并在设备矩阵里记录每台设备是否已投放。
- 目录名尽量用**脚本可控的固定语言**（`mf_noaudio` 这类），不要用设备本身的本地化目录名 —— 后者会随系统语言变。

## 不要碰的东西

- 不默认清应用数据（`pm clear` 一类）或用户草稿；即使只清缓存，也要明确功能归属、授权与场景前置。仅处理本轮专属测试数据，不能借其他功能目录。
- **不要并发跑同一台设备。** 两个 maestro 进程抢同一个设备会互相干扰，表现为随机失败。
- 跑之前确认没有其他任务正在操作目标设备；发现未知进程时不擅自终止。

## 顺序依赖

脚本之间可能有前置依赖（例如「功能场景都要求会员」）。这种依赖要：

- 写进每个 flow 的前置条件注释
- 在切换状态的那个脚本里明确写出「跑完之后哪些脚本的前置不再成立、怎么恢复」

不要把这类依赖藏在某个脚本的实现细节里。
