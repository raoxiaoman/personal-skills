# Android 业务埋点

先核对需求与真实上报链，不按字段名猜 API，也不把本地日志当成服务端接收证明。只有审查请求时给发现，不默认修改。

## 建立映射

确认目标项目、功能和需求版本，优先复用现有事件、常量和封装。缺少需求时可核对已给出的事件，但不能从新增代码反推“没有漏埋”。

每个事件至少记录：需求条目、实际 event name、参数/枚举、触发条件、排除条件、次数与生命周期；只有相关时再补 Retry、广告/Pro 解锁、失败分类、取消、保存及历史恢复。需求明确采用 Firebase `select_content` 时，逐项写出 `event_name=select_content`、`content_type=<业务 key>`、`item_id=<操作值>`；字段映射不等于已确认当前项目的封装 API。

VideoGuru 先读 [项目契约](references/videoguru.md) 并核对当前实现；其他项目先找自己的上报入口与过滤链，不因出现 `AppTrack` 或 `select_content` 就套同一映射。

## 实现与审查

- 事件放在需求语义真正成立的位置。需求统计点击就统计点击，统计实际开始就不能在校验失败时上报开始；成功、失败、取消、保存分别按需求定义。
- 使用项目现有常量分组、封装和过滤机制，不为一次性调用创建框架，不绕过过滤器强行发送。既有封装无法表达时先说明缺口。
- Retry 是否重计、重复回调如何处理、会话与执行代次如何区分，都按事件契约选择；不把所有事件机械改成 once，也不默认加 Boolean 门禁或修改任务 API。
- 区分本次新结果、历史恢复、页面重建和重复点击。需要幂等时按事件生命周期确定归属，避免屏幕重建导致重复或全局标记误抑制后续会话。
- 参数仅含已批准的稳定业务枚举或范围；不发送用户输入、账号、文件路径、原始异常或服务端原文。未知分类按需求处理，不擅自合并业务错误。
- 过滤、采样、同意状态和初始化可能影响发送。先定位证据，不为让日志出现而关过滤、重设同意或修改远端配置。

## 验证

先核对映射、调用点和受影响行为测试，再按项目实际语言/模块做最小编译。安装、启动和页面操作需要各自有效授权；用现有 Maestro 场景验证已授权的业务路径。

[验证与采集](references/verification.md) 提供同包公共 CLI 的用法；复用现有实现，不再复制日志解析器。不自动启动查看器、开启 Firebase Debug、清 logcat、重启应用或扩大到 SDK 初始化排障。

默认按需求核对应用侧事件的参数、次数和顺序；SDK 日志为辅助，服务端专项仅在明确要求时展开。区分过滤前日志、应用侧调用、SDK 观察和服务端接收；缺少 SDK 日志不单独证明业务未上报。

交付需求映射、代码位置、已验证场景、命令/产物及未覆盖范围。未运行场景、零事件、采集失败或旧包证据不算通过；日志数量也不等于业务唯一次数。不自动提交、发布或更新云端过滤配置。
